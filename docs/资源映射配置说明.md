# 天地劫（TDJ_Sword）资源映射配置说明

> 适用版本：`Sword.apk`（Unity 2021.3f1c1 / il2cpp）
> 对应工程：`Man/Client`；对应导出产物：`AssetDump/`
> 最后更新：2026-10-27

本文说明**游戏里的一份资源是怎么被找到、被谁引用、按什么规则画出来的**，覆盖动画、精灵与贴图、数据表、UI 四部分，并给出可直接对照的路径表。

## 1. 资源从 APK 到工程再到浏览副本

```
Sword.apk
├─ assets/bin/Data/data.unity3d        557 MB  ← 贴图/精灵/prefab/场景/动画组件
└─ assets/bin/Data/resources.resource  289 MB  ← 音效(FSB5/Vorbis)、视频(mp4/ogv)
        │
```

两条导出管线的差别：

| 项目 | `AssetDump/`（本说明的对照对象） | `Man/Client/Assets/Resources/Texture/`（工程用） |

| 目录 | `Sprite/<动画名>/<基名>_t<ID>.png`、`Texture2D/`、`AudioClip/`、`Video/` | `<动画名>/<基名>_t<ID>.png` |

| 索引页 | `index.html` | 无 |

> `AssetDump` 不能直接拷进工程：缺少 GUID 与导入设置，必须走 `export_assets.py`。

## 2. 动画系统

### 2.1 载体：一个动画 = 一个 prefab

- 路径：`Assets/Resources/Prefab/<animationName>.prefab`
- 例：`Assets/Resources/Prefab/Stage/Stage00/Eanm_01.prefab` 的 `animationName` 为 `Stage/Stage00/Eanm_01`
- 组件：`GameAnimation`（MonoBehaviour，脚本 fileID `951`），SAF 数据在构建期被烘焙进组件
- `sprites` 字段：1458 个动画 prefab 中 1456 个为空数组，运行时按命名规则去 `Resources/Texture` 取图（见 2.5）；只有 `Misc/MAP_VIE`、`Misc/Cha_tur` 两个预连了 `sprites`。

### 2.2 `GameAnimation` 关键字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `UI` | bool | `true` 走 uGUI `Image` 分支，`false` 走 `SpriteRenderer` 分支 |
| `animationName` | string | 动画名，同时是 prefab 路径与贴图目录名 |
| `safHead.count1` | short | 帧数（`saf1` 长度） |
| `safHead.count2` | short | 精灵数（`saf2` 长度 = 该动画图片总数） |
| `safHead.count3[32]` | short[] | 按动作类型分组的帧数，下标对应 `GameAnimationType` |
| `saf1[]` | SAF1[] | 每帧：音效号、时长、受击/变色/震屏标记、图层列表 |
| `saf2[]` | SAF2[] | 每个精灵的尺寸（SAF 单位，×2 = 像素） |
| `pivot` | Vector2 | 默认 `(0,1)` 左上角；`(0,0)` 时触发水平镜像 |
| `offsetX` / `offsetY` | int | 整组位移（屏幕中心为原点） |
| `playSound` | bool | 是否播放帧音效 |
| `otherGameAnimation` | GameAnimation | 跨动画叠加（如角色带武器/特效）时由战斗逻辑运行时赋值 |
| `color` | Color | 整组染色，与每层 alpha 相乘 |

### 2.3 SAF 二进制格式（字节级）

`GameAnimation.load()` 的逆写格式，全部小端：

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | i16 | `count1` | 帧数 |
| 2 | i16 | `count2` | 精灵数 |
| 4 | i16 × 32 | `count3[32]` | 各动作帧数，下标 0=Stand 1=Move 2=MoveStart 3=MoveEnd 4=Win 5=Skill，其余保留 |
| 68 | — | `saf1[count1]` | 帧表，见下 |
| … | — | `saf2[count2]` | 每个精灵 `i16 width, i16 height` |

`SAF1`（每帧，固定 10 字节 + 图层数组）：

| 类型 | 字段 | 说明 |
|---|---|---|
| i16 | `sound` | 音效号，`-1` 表示无；对应 `Sound/<id>` |
| i16 | `time` | 停留帧数；实际时长 `frameTime = 0.04 + time × 0.04 + delay`（秒），即基准 25fps |
| u8 | `hit` | 受击判定标记 |
| u8 | `color` | 染色标记 |
| u8 | `shake` | 震屏标记 |
| u8 | `unknow4` | 未使用 |
| i16 | `count` | 图层数 |
| — | `saf11[count]` | 图层数组 |

`SAF11`（每层，13 字节）：

| 类型 | 字段 | 说明 |
|---|---|---|
| u16 | `textureID` | **图片索引**，对应 `saf2` 下标，也是文件名 `_t<ID>` 的来源；`>= 0x8000` 时不是本动画的图，而是取 `otherGameAnimation` 第 `ID-0x8000+1` 帧第 0 层贴图 |
| i16 | `textureX` | 图层左上角 X（SAF 单位，×2 = 像素） |
| i16 | `textureY` | 图层左上角 Y（SAF 单位，向下为正） |
| u8 | `textureType` | 材质类型 0~7，见 2.7 |
| i16 | `unknow8` | 与 `unknow10` 配合控制透明度（见 2.6） |
| i16 | `unknow10` | `16` 表示按 `unknow8 × 0.05` 计算 alpha |
| i16 | `unknow12` | 未使用 |

> 代码里 `count1/count2` 用 `BitConverter.ToInt32` 读取但只前移 2 字节，实际生效仍是 i16；逆写时按 i16 处理即可。

### 2.4 帧索引布局

SAF 里所有帧是**一条连续数组**（`saf1[0..count1-1]`）。用哪种方式取帧，取决于动画类型：

**A. `count3` 全零的动画（1231 / 1533）**

过场（`Stage/*`）、特效（`Magic/*`）、界面（`Misc/*`）等属于这一类，`count3` 不表达动作分组，播放时由调用方直接给帧范围：

| 接口 | 行为 |
|---|---|
| `playAnimation(s, e, loop)` | 从第 `s` 帧播到第 `e` 帧（`e < 0` 表示到 `count1-1`） |
| `showFrame(f)` | 只显示第 `f` 帧（战斗地面 `FLOOR_` 就是这么用的） |

**B. `count3` 非零的动画（302 / 1533，主要是单位动画）**

按 `GameAnimationType` 分区，每区再按 4 个方向平铺。代码中的起始帧累加顺序：

| 动作 | 起始帧（代码推导） | 循环 |
|---|---|---|
| 前置 2 帧（Skill 用） | `[0, 2)` | — |
| 胜利 Win | `2` | 否 |
| 站立 Stand | `2 + W' + dir × count3[Stand]` | 是 |
| 移动 Move | `2 + W' + count3[Stand]×4 + dir × count3[Move]` | 是 |
| 起步 MoveStart | 再累加 `count3[Move]×4` | 否 |
| 停步 MoveEnd | 再累加 `count3[MoveStart]×4` | 否 |
| 技能 Skill | 固定 `[0, 2)` | 是 |

其中 `W' = count3[Win]`，为 0 时代码按 1 占位。
`playAnimationRPG` 没有前置 2 帧，`Stand` 从 `dir × count3[Stand]` 直接开始。

方向枚举：`South=0, West=1, North=2, East=3`。

> **取帧时不要用 `count1` 反推布局**：实测 302 个带 `count3` 的动画里，只有 11 个满足 `2 + W' + (Stand+Move+MoveStart+MoveEnd)×4 == count1`，其余存在 2~13 帧的额外保留/非常规排布（例如 `Sprite/man213/213MAN`：`count1=37`，按公式算 35）。
> 需要精确切帧时，应按运行时逻辑（`playAnimationBattle` / `playAnimation` / `showFrame`）或直接按 `saf1` 顺序取——每帧数据本身是完整自洽的。

### 2.5 运行时取图规则

`updateFrame()` 中每帧对每个图层执行：

```
// 1. 优先用 prefab 里预连的 sprites 数组
if (sprites != null && sprites.Length > 0)
    sprite = sprites[textureID];
// 2. 否则按命名规则加载
else {
    sprite = Resources.Load<Sprite>("Texture/" + animationName + "_t" + textureID);
    if (sprite == null) {
        // animationName = "Stage/Stage00/Eanm_01" → 末段 "Eanm_01"
        sprite = Resources.Load<Sprite>("Texture/" + animationName + "/" + 末段 + "_t" + textureID);
    }
}
```

即两条候选路径：

| 优先级 | 路径 |
|---|---|
| 1 | `Texture/<动画名>_t<ID>` |
| 2 | `Texture/<动画名>/<动画名末段>_t<ID>` |

本工程导出的实际落盘为第 2 种：`Assets/Resources/Texture/Stage/Stage00/Eanm_01/Eanm_01_t12.png`。
`AssetDump` 与之等价：`AssetDump/Sprite/Stage/Stage00/Eanm_01/Eanm_01_t12.png`。

> 名字大小写注意：代码拼的是小写（如战斗单位 `Prefab/Sprite/man001/001man`），而资源实际名是 `001MAN`。Unity 的 Resources 查找不区分大小写，所以能取到；但自建加载器（或按大小写敏感方式反解）时会出现“找不到/串图”。

### 2.6 图层合成规则

同一帧的图层按 `saf11` 数组顺序绘制，UI 与非 UI 两个分支：

| 规则 | UI 分支（`UI=true`） | 世界分支（`UI=false`） |
|---|---|---|
| 容器 | `Prefab/Image`（uGUI `Image` + `CanvasRenderer`） | `Prefab/Sprite`（`SpriteRenderer`） |
| 位置 | `anchoredPosition = (textureX + offsetX, -textureY + offsetY)` | `localPosition = (textureX + offsetX, -textureY + offsetY, -i)` |
| 尺寸 | `sizeDelta = sprite.rect.size × 0.5` | 由 `SpriteRenderer` 按 sprite 原始尺寸（导入 PPU=2） |
| 缩放基准 | 0.5（1 SAF 单位 = 2 像素） | 同上 |
| 层级 | `textureType == 7` → `SetAsFirstSibling()`（压到最底） | `textureType == 7` → z 取 `+i`（压在其它层之上） |
| 镜像 | `pivot == (0,0)` → `localScale.x = -1`，位置改为 `w + textureX + offsetX` | 无（`pivot` 只在 UI 分支生效） |
| 材质 | `GameMaterialConfig.getMaterial(textureType)` | 同左 |
| alpha | `textureType==2 && unknow10==0` 时按 Type0 处理；`unknow10==16` → `alpha = min(unknow8 × 0.05, 1)` | 同左 |

补充：

- `pivot` 默认 `(0,1)`，即图层左上角对齐 `(textureX, textureY)`；
- 每层的 `sprite.rect` 是**未裁剪框**，真正像素区是 `textureRect`，二者差值决定内容在框内的偏移（导出时已按此还原）；
- 图层顺序即 `saf11` 顺序，世界分支用 `-i` 做 z，所以**数组越靠后越靠前**（`textureType==7` 例外）。

### 2.7 材质（`textureType` → `Material/TypeN`）

`GameMaterialConfig.getMaterial(i)` 直接取 `Resources/Material/Type<i>`，i ∈ 0..7：

| textureType | 材质 | 对应 Shader | 备注 |
|---|---|---|---|
| 0 | `Material/Type0` | `Game/Type0` | 常规层；顶点色为黑时 RGB×2 提亮，`Cull Off` |
| 1~7 | `Material/Type1` ~ `Type7` | `Game/TypeN` | 均为透明混合（`SrcAlpha OneMinusSrcAlpha`，`ZWrite Off`），差异在 shader 内部处理；7 另有层级置底/置顶语义 |

### 2.8 帧音效

```csharp
if (saf1[f].sound != -1 && playSound)
    GameMusicManager.instance.playSound("Sound/" + saf1[f].sound);
```

即 `saf1[f].sound` 就是 `Resources/Sound/<id>.wav` 的文件名（无补零）。`AssetDump/AudioClip/<id>.wav` 与之对应。

## 3. 精灵与贴图

### 3.1 关系

```
Texture2D（图集，9937 张）
   └─ Sprite（图集切片，85464 个）  ── 用 rect / textureRect 从图集裁出
        └─ GameAnimation.saf1[f].saf11[i].textureID  ── 按序号引用
             └─ Resources/Texture/<动画名>/<基名>_t<ID>.png
```

- 一个动画的图片集合 = `saf2[0..count2-1]`，第 i 张的文件名固定为 `<动画名末段>_t<i>.png`；
- `sprites[i].m_Name` 与 `<基名>_t<i>` 一一对应（已抽样 614/614 验证）；
- 同一张 Sprite 可以被多个动画引用（导出时各动画目录各放一份）。

### 3.2 命名规范

| 资源 | 规范 | 示例 |
|---|---|---|
| 贴图切片 | `<动画名末段>_t<textureID>.png` | `Eanm_01_t12.png` |
| 动画 prefab | `<animationName>.prefab` | `Stage/Stage00/Eanm_01.prefab` |
| 音效 | `<数字 id>.wav` | `208.wav` |
| 音乐 | `Music_<两位编号>.wav` | `Music_07.wav` |
| 视频 | `<名字>.mp4` / `.ogv` | `Title.mp4`、`M70.ogv` |

### 3.3 重名问题（重要）

APK 里 **Sprite 的 `m_Name` 不是唯一键**：3463 个名字对应多个对象，全量 85464 个精灵只有 75087 个唯一名。例如 `Eanm_01_t12` 同名有 18 份，最大的一份是 1024×512 的火焰图，而 `Stage/Stage00/Eanm_01` 动画真正引用的是 58×89 的角色图层。

因此：

- **禁止**按名字把全部同名 Sprite 导出成一张图（会串图）；
- 正确做法是读 `GameAnimation.sprites[]` 的引用顺序；
- 另外存在**只差大小写**的不同资源（如 `EANM_01_t0` 与 `Eanm_01_t0` 是两张不同的图），在 macOS/Windows 这类大小写不敏感的文件系统上会互相覆盖，导出时必须按小写判重并加后缀区分。

#### 3.3.1 没有 typetree 时如何拿到 `sprites[]`

构建版 `data.unity3d` 不含 MonoBehaviour 的 TypeTree，`UnityPy` 的 `read_typetree` 会失败。此时用**字节解析**兜底（已集成进 `tools/export_assets.py`）：

1. 以 SAF 目录里的动画名（`Objects/SAF/**/*.saf` 的相对路径）为锚点，在 MonoBehaviour 原始字节里搜同名 ASCII 串；
2. 命中后，在该对象内从偏移 28 开始向后扫描**最长的 PPtr 连续段**（每项 12 字节：`int32 fileID` + `int64 pathID`，且 pathID 必须指向真实存在的 Sprite）；
3. 该连续段即 `sprites[]`，元素个数应与 SAF 头部的帧数一致 —— 实测 1215 个动画 **100% 吻合**，可作自检。

#### 3.3.2 全量校验结果

用上述引用对工程内 **76671 帧**逐帧裁切比对（像素差 >1% 视为不一致），实测 **172 帧取错**：

| 目录 | 帧数 | 典型原因 |
|---|---|---|
| `Sprite/man162` | 113 | `161A` 系列误用 man161 的图 |
| `Sprite/man016` | 16 | `002MAN` 误用 man002 的图 |
| `Stage/Stage15` | 9 | `Eanm_16`、`Eanm_09` |
| 其余 Sprite / Stage / Misc / Magic | 34 | `Cha_tur`、`Man_eff`、`M2`、`Eanm_08` 等 |

修复只覆盖内容不一致的 PNG，`.meta`（guid / pivot / ppu）保持不变；复查后 76671 帧全部一致。

### 3.4 像素解码规则（导出侧）

| 问题 | 处理 |
|---|---|
| 像素流方向 | Unity 纹理自下而上存储，解码后必须整体垂直翻转 |
| 图集裁剪 | 按 `rect`（未裁剪框）+ `textureRect`（实际像素）还原，`top = 图集高 - (y + h)` |
| 压缩格式 | ETC2 / ETC2A8 / BC1 / BC3；其中 Crunch 包（格式 64/65）需先 `unpack_unity_crunch` |
| 特殊格式 | RGB565（如 `map17`）、RGBA32、RGB24 单独处理 |
| 导入设置 | 工程侧 `.meta`：`textureType=8`（Sprite）、`spritePixelsToUnits=2`、`alignment=9`、pivot 取 Sprite 自带值 |
| 资源定位 | 像素在 `.resS` 里。APK 的 `data.unity3d` 是 bundle，`resources.assets.resS` 位于 `BundleFile.files` 内层，不在 `env.files` 顶层；按平铺目录读取会拿不到数据 |

格式分布（9937 张）：ETC2+Crunch 5617、ETC2A8+Crunch 4084、ETC2A8 227、RGBA32 4、RGB24 4、RGB565 1。

### 3.5 Sprite 的 fileID（场景/prefab 引用）

场景与 prefab 里 `m_Sprite` 是 `{fileID, guid}` 二元组，`fileID` 由图片的 `spriteMode` 决定：

| 图片类型 | `spriteMode` | `fileID` |
|---|---|---|
| 单图 Single | 1 | 固定 `21300000` |
| 多切片图集 Multiple | 2 | `21300002`、`21300006`、`21300008`… 切片号 |

导出的每张 PNG 都是**单图**，所以指向它的 `m_Sprite` 必须是 `21300000`。若沿用原版图集的切片号（如 `21300026`），运行时会取到 `sprite == null`，`Image` 退化成**纯白矩形** —— 行囊/商铺面板整块变白就是这个原因（`Item_win_t12` / `Item_win_t13` 共 6 处引用）。

**但不要盲目批量替换**：工程里仍有真正的多切片图集，例如 `EasyTouchBundle` 的 `ETCDefaultSprite.png`（`spriteMode: 2`），虚拟按钮用的就是 `21300002/06/08/28` 这些切片号，改成 `21300000` 会把按钮变成整张图集。

判定与修正：

```bash
# 1) 列出场景里所有非 21300000 的 sprite 引用及其 guid
grep -o 'm_Sprite: {fileID: [0-9]*, guid: [0-9a-f]*' Scenes/*.unity | grep -v 21300000

# 2) 查该 guid 对应 PNG 的 spriteMode
grep -H 'spriteMode' $(grep -rl '^guid: <guid>' --include='*.png.meta' .)

# 3) 只有 spriteMode: 1 的才把 fileID 改成 21300000，spriteMode: 2 的原样保留
```

## 4. 数据表

### 4.1 运行时数据在哪

游戏发布版**不读 DAT 文件**。各 `Game*Data` 类都是 `Singleton<T>`，数据以 `[SerializeField]` 数组形式**序列化在场景里**（`level0`=TitleScene 为主，部分在其它场景），启动时由 Unity 反序列化直接得到。

例：`GameUnitData` 定义 `[SerializeField] GameUnit[] data;`，实测 `level0` 中有 116 个单位。

## 5. UI

### 5.1 UI 动画与普通动画的区别

同一套 `GameAnimation`，靠 `UI` 字段切换渲染分支（见 2.6）：

- **世界/战斗动画**：`UI=false`，容器是 `Prefab/Sprite`（`SpriteRenderer`），z 用 `-i` 排序；
- **UI 动画**：`UI=true`，容器是 `Prefab/Image`（uGUI `Image`），位置用 `anchoredPosition`，尺寸用 `sizeDelta`。

APK 内 `UI=1` 的动画共 **69 个实例**，全部在场景里（`level0`~`level3`），不在 `resources.assets`，因此不影响 `Resources/Prefab` 的 1457 个世界动画。出现的 UI 动画名：

| `Misc/MSG_BOX` | 对话框 | level1(5)、level3(5) |
| `Misc/Item_win` | 物品/背包窗口 | level1(8)、level2(8) |
| `Misc/ITEM_MEN` | 道具菜单 | level1(2)、level2(2) |
| `Misc/Man_pro` | 单位信息面板 | level2(5)、level3(5) |
| `Misc/SP_REV` | 特技/法术展示 | level2(17) |
| `Misc/CAMP_MEN` | 营地菜单 | level2(1) |

### 5.3 场景里的 UI 不是按名字加载

菜单/界面上的静态图片（按钮、边框、标题、图标等）是场景与 prefab 里**直接按 GUID 引用**的 `Sprite`，没有命名规则可循。

这类资源无法通过“名字 → 路径”反查，只能：

1. 在场景 YAML 里读 `m_Sprite: {fileID, guid}`，再用 guid 反查资产名；或
2. 直接从 `AssetDump/Texture2D` 里按图找人（`index.html` 可搜索）。

## 7. 校验清单

1. **帧数**：`safHead.count1 == saf1.Length`（恒成立，可作为解包自检）。
2. **精灵数**：`safHead.count2 == saf2.Length`，且该动画目录下有 `count2` 个 `_t0 ... _t<count2-1>.png`。
3. **完整性**：遍历所有 `saf11.textureID`，必须满足 `0 <= textureID < count2`，且对应文件存在。
4. **动作区间**（仅 `count3` 非零的单位动画）：抽查 `playAnimationBattle(Stand, South)` 的首帧是否为人物的正面站立；若偏移 ±2 帧，说明该动画有额外保留帧，按实际观感校正，不要硬套公式。
5. **像素方向**：随便抽一张含文字的图（如 `Title`），文字应为正向；否则是漏了垂直翻转。
6. **裁剪正确**：抽帧图不应出现整张图集的其它内容；边缘透明边框应与 `rect` 一致。
7. **重名**：同一动画内 `_t<ID>` 唯一；跨动画同名精灵不是同一资源，不能按名字合并。
8. **大小写**：检查导出目录同级是否出现仅大小写不同的文件（会被文件系统合并）。
9. **Sprite 引用**：场景/prefab 里 `m_Sprite` 的 `fileID`，单图必须是 `21300000`，多切片图集才允许其它值（见 3.5）。批量修正前先按 `spriteMode` 区分，否则会误伤虚拟按钮等图集切片。
